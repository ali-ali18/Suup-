# Pesquisa: backend embutido no app, VPS e sincronização

Data da pesquisa: 19/11/2026. Base para a decisão de arquitetura do app de desktop com uma escolha "Este computador / Minha VPS". Ver também [fase-4-app-windows-e-modo-local.md](fase-4-app-windows-e-modo-local.md), [REDE.md](../REDE.md) e [apps/desktop/README.md](../../apps/desktop/README.md).

## Pergunta

Pergunta do dono: "Dá para embutir o backend no app? e usar na VPS em sync? o Hermes faz isso… no Grok é apenas um app."

1. Como o Hermes Agent (NousResearch/hermes-agent) faz o desktop, o backend e o uso remoto ou na VPS: o agente roda dentro do app, em processo filho, em Python empacotado? Existe modo servidor? Como o app e uma instância remota se relacionam (um cérebro? sync? o que sincroniza)? Onde fica o estado? Mesma pergunta, de forma breve, para OpenClaw, OpenBot e OpenMausBot.
2. Como fazer um sidecar Tauri 2 para um backend Node: `bundle.externalBin`, permissões do plugin shell, ciclo de vida (subir ao abrir, encerrar ao sair, reinício após queda), empacotar Node (Node SEA e alternativas), tamanho e particularidades do Windows.
3. Opções de Postgres embutido: PGlite (WASM; extensões `pgvector`, `unaccent`, configuração de busca `portuguese`; LISTEN/NOTIFY; limite de conexões; persistência em diretório) e Postgres nativo empacotado (`embedded-postgres`, binários zonky): fatos e licenças.
4. Sincronização entre instância local e VPS: como ElectricSQL, PowerSync e Rocicorp Zero sincronizam com Postgres, o que cada um sincroniza, resolução de conflito, e se suportam servidor como autoridade com cache no cliente. Problemas específicos de um harness de agente. O modelo mais simples "um cérebro, escolhe o servidor" e a documentação de fornecedores que o recomenda.
5. Grok Bot: o que é público sobre a estrutura do app da xAI.

## Fatos verificados

### 1. Hermes Agent: desktop, backend e uso remoto

1.1. **O desktop não é um processo só.** O app é Electron (`apps/desktop/package.json:195`, `"electron": "44.10.2"`). Ele sobe o backend como processo filho: "On POSIX the backend IS spawned into its own session/process-group (start_new_session=True)" (`apps/desktop/electron/backend-child.ts:12`). O backend anuncia pronto com `HERMES_BACKEND_READY`, vindo de `hermes serve` (`apps/desktop/electron/backend-ready.ts:3`).

1.2. **Python empacotado.** O pacote `bundled` tem o runtime local: "`bundled` carries the local runtime." (`apps/desktop/BUILDING.md:19`). Conteúdo: "Pinned CPython and uv, plus a ready Python dependency tree." (`apps/desktop/BUILDING.md:28`). A variante `light` é "a remote-only client without Python or a local agent" (`apps/desktop/BUILDING.md:20-21`).

1.3. **Um backend por host, o app se anexa a ele.** "Exactly ONE `hermes serve` runs per HOST and multiplexes every profile, so Desktop must ATTACH to a backend that is already listening and spawn only when the host has none." (`apps/desktop/electron/backend-discovery.ts:3-4`).

1.4. **Primeira execução: conectar ou instalar.** "first launch lets you connect to an existing Hermes gateway or install Hermes locally" (`apps/desktop/README.md:39`). A resolução cai em "bootstrap-needed, which shows the first-run choice (connect a remote, or install)" (`apps/desktop/electron/backend-resolution.ts`, comentário do topo).

1.5. **Fontes múltiplas, sem sincronização.** O registro de conexões tem `export type ConnectionKind = 'cloud' | 'local' | 'remote' | 'ssh'` (`apps/desktop/electron/connection-registry.ts:50`), e as fontes são "all registered at once" (`connection-registry.ts:8`). O texto diz que mudanças de roteamento "land separately" (`connection-registry.ts:8-9`). Não há mecanismo de réplica de estado entre o app e a instância remota.

1.6. **Falha não cria réplica local.** "Remote SSH, URL and OAuth routing retain their existing authentication paths; failure never creates a local replacement." (`apps/desktop/docs/canonical-gateway-protocol.md:3-7`).

1.7. **Estado em SQLite por perfil.** `_KNOWN_PROVIDERS = ("sqlite",)` (`persistence_assembly.py:44`); "An absent section or file means ``sqlite``." (`persistence_assembly.py:142`). O arquivo é `state.db`: "``state.db`` file" (`persistence/sqlite/_backend.py:4`). A pasta padrão é `~/.hermes` (`hermes_constants.py:77`, `user_home() / (".hermes" + suffix)`). No Windows nativo fica em `%LOCALAPPDATA%\hermes` (README, linha 61).

1.8. **Execução em vários lugares.** "Six built-in terminal backends — local, Docker, SSH, Modal, Daytona, and Vercel Sandbox" (README, linha 29). "Run it on a $5 VPS, a GPU cluster… talk to it from Telegram while it works on a cloud VM." (README, linha 19).

1.9. **Gateway de mensagens separado.** "hermes gateway      # Start the messaging gateway (Telegram, Discord, etc.)" (README, linha 115). O README diz que Telegram, Discord e os outros passam por "a single gateway process" (linha 25).

1.10. **Antivírus.** "If your antivirus (Bitdefender, Windows Defender, etc.) quarantines `uv.exe` … this is a **false positive**… ML-based antivirus engines commonly flag unsigned Rust binaries that download and install packages." (README, linha 74). O caso é o `uv.exe`, não o backend, mas mostra o risco de binário não assinado baixando e instalando coisas no Windows.

1.11. **Mesmo agente em todas as superfícies.** "Same agent, same skills, same memory as the CLI and gateway" (`apps/desktop/README.md`, linha 10).

### 2. OpenClaw

2.1. **Um Gateway por host.** "One Gateway per host. It is the only place that opens a WhatsApp session." (`docs/concepts/architecture.md`, linha 17). "OpenClaw runs one Gateway (the master) on a host and connects every client to it. The Gateway owns sessions, auth profiles, channels, and state; everything else is a client." (`docs/gateway/remote.md`, parágrafo de abertura).

2.2. **Apps são nós conectados por WebSocket.** "A **node** is a companion device (macOS/iOS/watchOS/Android/headless) that connects to the Gateway with `role: \"node\"`" (`docs/nodes/index.md`, linha 13). No macOS, o app de barra de menu "connects to the Gateway's WS server as one node" e "remains the sole Gateway connection and node identity" (`docs/nodes/index.md`, linhas 15-20).

2.3. **Acesso remoto por Tailscale ou SSH, com loopback.** "The Gateway WebSocket binds to **loopback** by default, on port `18789`" (`docs/gateway/remote.md`, linha 97). "For the always-on and laptop setups, prefer keeping `gateway.bind: \"loopback\"` and using **Tailscale Serve** for the Control UI… SSH tunnel is the fallback that works from any machine." (`docs/gateway/remote.md`, linha 107).

2.4. **Estado no hardware do dono.** "State, memory, and credentials live on your hardware." (README, linha 20). Caminhos configuráveis por `OPENCLAW_STATE_DIR` (`docs/gateway/index.md`, linhas 198-205).

2.5. **Ferramentas no host.** "Tools run on the host for the main session unless you configure sandboxing." (README, linha 81).

2.6. **Continuidade remota é a mesma conversa do Gateway.** "Remote clients can continue the same Gateway-owned conversation by URL or short reference." (`docs/gateway/remote.md`, linhas 13-14). Não encontrei sincronização entre cópias.

2.7. **Versão e licença.** Pacote 2026.11.5, MIT, `engines` `>=24.16.0 <25 || >=26.1.0` (`package.json` do repositório).

### 6. Tauri 2: sidecar

6.1. "The `externalBin` configuration expects a list of strings targeting binaries either with absolute or relative paths." (https://raw.githubusercontent.com/tauri-apps/tauri-docs/v2/src/content/docs/develop/sidecar.mdx). Exemplo da fonte: `"externalBin": ["binaries/my-sidecar"]` exige `src-tauri/binaries/my-sidecar-x86_64-unknown-linux-gnu` no Linux e `my-sidecar-aarch64-apple-darwin` no Mac com Apple Silicon (sidecar.mdx, linha 35).

6.2. Nome por plataforma: "Tauri will look for system-specific binaries following the pattern 'binary-name{-target-triple}{.system-extension}'" (`crates/tauri-utils/src/config.rs:1976-1984`, campo `pub external_bin: Option<Vec<String>>` na linha 1986). No Windows, o arquivo termina em `.exe`, com o triplo alvo antes dele (exemplo `my-binary-x86_64-pc-windows-msvc.exe` no mesmo comentário). Cada alvo precisa do seu binário.

6.3. Permissão: "shell:allow-execute" com `"sidecar": true` no objeto da capacidade (sidecar.mdx, linhas 135-146). O escopo tem `pub sidecar: bool`, "If this command is a sidecar command." (`plugins/shell/src/scope.rs`, linhas 72-73). Chamada no Rust: `app.shell().sidecar("my-sidecar")` (sidecar.mdx, linha 93).

6.4. **Encerramento ao sair.** "all spawned child processes are killed when the application exits." (`plugins/shell/src/lib.rs`, doc de `init`). A implementação mata os filhos no evento `RunEvent::Exit` (`plugins/shell/src/lib.rs`, bloco `.on_event`). Isso não roda se o app for morto à força.

6.5. **Drop não mata por padrão.** `kill_on_drop` é `false` na construção (`plugins/shell/src/process/mod.rs:234`), e o `Drop` só mata se `kill_on_drop` estiver ligado (`process/mod.rs:134-141`).

6.6. **Reinício após queda.** Não encontrei nada no plugin que reinicie o processo. O evento `CommandEvent::Terminated` existe (`process/mod.rs`, enum de eventos), então a supervisão deve ser feita pelo app (ver "Inferências").

### 7. Node: empacotamento como executável único (SEA)

7.1. "> Stability: 1.1 - Active development" (`doc/api/single-executable-applications.md`, linha 24).

7.2. `--build-sea` foi adicionado na v25.5.0 (cabeçalho YAML do mesmo arquivo). O fluxo antigo usava `postject` e `--experimental-sea-config` (linhas ~775-780).

7.3. Assinatura: "Sign the binary (macOS and Windows only)" (linhas 72-82). No Windows é opcional, e "A certificate needs to be present for this to work."

7.4. "The version of the Node.js binary used to produce the blob must be the same as the one to which the blob will be injected." (linhas ~129-130).

7.5. Módulos nativos: "Native addons (`.node` files) cannot be loaded directly from the VFS because `process.dlopen()` requires files on the real file system." (linhas 437-438). É preciso extrair o `.node` para o disco.

7.6. `pkg`: "`pkg` has been deprecated with `5.8.1` as the last release." (https://raw.githubusercontent.com/vercel/pkg/main/README.md). Bun lista "Single-file executable" na sua documentação (README do Bun, linha 157), mas a página de detalhe não foi lida.

### 8. PGlite e Postgres embutido

Fatos da documentação e do pacote:

8.1. "PGlite is single user/connection." (README, seção Limitations). "PostgreSQL typically operates using a process forking model… programs compiled with Emscripten… cannot fork new processes" (README, seção How it works).

8.2. "It is only 3mb gzipped and has support for many Postgres extensions, including pgvector and PostGIS." (README, linha 36). O pacote 0.5.17 traz `contrib/*.tar.gz` com `unaccent.tar.gz`, `uuid-ossp.tar.gz`, `pg_trgm.tar.gz`, `pgcrypto.tar.gz` e outros. Não traz `vector`. O pgvector vem em pacote separado: `@electric-sql/pglite-pgvector` 0.0.18, com `CREATE EXTENSION IF NOT EXISTS vector;` (README do pacote).

8.3. Tamanhos no pacote 0.5.17: `pglite.wasm` 9.118.807 bytes e `pglite.data` 6.241.295 bytes.

8.4. API `listen(channel: string, callback: (payload: string)…)` em `dist/interface-ymvJB3xs.d.ts` (pacote 0.5.17).

8.5. Sockets: "Although PGlite is a single-connection database, it is possible to open and use multiple simultaneous connections with pglite-server… through a multiplexer… This is different from a normal Postgres installation, so not all use cases are guaranteed to work." (README de `@electric-sql/pglite-socket`). E: "SSL connections are **NOT** supported." (mesmo README).

8.6. Zonky para Windows x64 18.7.0 contém `share/extension/unaccent.control`, `share/tsearch_data/portuguese.stop`, `lib/dict_snowball.dll`. Não há nenhum arquivo com `vector` na listagem de 1578 entradas.

8.7. A matriz de plataformas do `embedded-postgres` inclui Windows x64 para as versões 14.25.0 a 18.7.0 (README do pacote, seção "PostgresQL Versions").

8.8. Licença do PostgreSQL: "Permission to use, copy, modify, and distribute this software and its documentation for any purpose, without fee, and without a written agreement is hereby granted" (COPYRIGHT do repositório `postgres/postgres`).

Resultados dos meus testes (versão PGlite 0.5.17, pgvector 0.8.7 dentro dele, PostgreSQL 18.7):

8.9. **Extensões.** `CREATE EXTENSION vector` e `unaccent` funcionam. `embedding <-> '[1,2,2.9]'` devolve o vizinho certo. `unaccent('ação')` devolve `acao`. A versão do pgvector é `0.8.7` (`pg_extension.extversion`). A imagem de produção do Suup usa `pgvector/pgvector:0.8.1-pg18` (`docker-compose.prod.yml:39`).

8.10. **Busca em português.** `to_tsvector('portuguese', 'Os gatos correram rapidamente pelas casas')` deu `'cas':6 'corr':3 'gat':2 'rapid':4`, e `to_tsquery('portuguese','gato & correr') @@ …` deu `true`. Não comparei a saída com um PostgreSQL nativo.

8.11. **Todas as migrações do Suup aplicam.** Executei os 19 arquivos de `packages/db/migrations/` em ordem, com `db.exec`, sem erro. Resultado: 28 tabelas no schema `public`. `suup_unaccent('ação')` = `acao`. Isso não passou pelo `packages/db/src/migrate.ts`, nem pela suíte de testes do Suup.

8.12. **LISTEN/NOTIFY no processo.** `listen` recebeu `"42"` de um `pg_notify` direto. Um gatilho `AFTER INSERT` com `pg_notify` recebeu os dois ids (`"1"`, `"2"`), como o `change_log` do Suup (`0006_change_feed.sql`).

8.13. **Concorrência e persistência no processo.** 200 consultas paralelas em 39 ms. Depois de `close()` e reabertura do mesmo diretório, a tabela continuou com o dado. Abrir o banco levou 2,9 s no primeiro teste (inclui carregar o WASM).

8.14. **Pelo socket, com o driver do Suup.** Com `PGLiteSocketServer` (0.2.20) e `postgres` 4.1.1 (`max: 10`): `select`, `vector` e 100 consultas paralelas funcionaram (72 ms). **`sql.listen(...)` não entregou nenhuma notificação**, nem a enviada pelo próprio socket, nem a enviada direto pelo PGlite (dois testes, `payloads []`). A causa não foi investigada.

### 9. Sincronização: o que cada produto sincroniza

9.1. **ElectricSQL.** "Electric is a read-path sync engine for Postgres. It syncs data out of Postgres into ... anything you like." Para rodar: "have a Postgres database with logical replication enabled; and then… run Electric in front of it, connected via `DATABASE_URL`" (README, seção What is Electric / Getting Started). A descrição é de sincronização de leitura. O README não descreve escrita.

9.2. **PowerSync.** "keeps a client-side SQLite database in sync with your backend database. Changes appear across users and devices in real-time, user interactions feel instant and your app continues to work even when offline. Supports Postgres, MongoDB, MySQL, and SQL Server." (README do monorepo). O SDK web é `@powersync/web` 2.7.0.

9.3. **Rocicorp Zero.** "The main client library. It uses replicache under the hood." (`packages/zero-client/README.md`). Há `packages/zero-cache` (servidor) e `packages/zql` (motor IVM). O README do monorepo diz que testes de `zero-cache`, `zql` e outros "were removed from the published repository on September 30, 2026" (README do monorepo). Não li a documentação de conflitos.

9.4. **Tailscale.** Não há recomendação do Tailscale no README do repositório, que descreve o daemon (`tailscaled`) e o CLI. A recomendação para acesso remoto aparece na documentação do OpenClaw (`docs/gateway/remote.md`, linha 107): "using **Tailscale Serve** for the Control UI, or a trusted LAN/Tailnet bind…; SSH tunnel is the fallback".

O servidor usa `LISTEN` numa conexão própria, aberta pelo `postgres` (`packages/server/src/stream/db-source.ts:179`).

## Inferências

Rotuladas. São conclusões minhas a partir dos fatos acima, não afirmações das fontes.

I1. **Nenhum dos produtos lidos sincroniza estado entre app e servidor.** Hermes: "failure never creates a local replacement" e fontes registradas, sem réplica. OpenClaw: clientes continuam a conversa do Gateway. OpenBot: importa agentes e não histórico. OpenMausBot: um harness local, computadores de nuvem separados. O padrão real é "um cérebro por vez, escolhido pelo usuário", com migração ou importação pontual. A resposta à pergunta "o Hermes faz sync?" é: embutido e remoto, sim; sincronização de dados, não encontrada.

I2. **A intuição sobre o Grok está certa no produto, e errada na estrutura.** Na página pública, o app é cliente e o trabalho roda em computadores de nuvem por bot. O mesmo vale para o OpenMausBot, que também tem computador de nuvem por bot.

I3. **PGlite serve para o schema atual, mas não para o modelo atual de processos.** As 19 migrações e as extensões usadas funcionam (fatos 8.9 a 8.11). O problema é a conexão: PGlite é de uma conexão, e pelo socket o `LISTEN` não entregou notificações (fato 8.14). Se o embutido usar socket, o stream cai em leitura periódica (a própria migração 0006 prevê isso). Se o servidor e o worker rodarem no mesmo processo, dá para usar a API em processo (`listen` funcionou no fato 8.12), mas isso muda o `packages/db`, que hoje usa o driver `postgres`.

I4. **Os testes não provam carga.** 200 consultas em 39 ms não dizem nada sobre transações longas, bloqueios (a migração 0007 usa `pg_advisory_xact_lock`, não testado no PGlite) e o worker de vários bots escrevendo ao mesmo tempo.

I5. **Node SEA é arriscado para a data de hoje.** O estado é "Active development", o `--build-sea` existe desde a v25.5.0, e o projeto fixa Node 22 (`.nvmrc`). Ou o projeto sobe a versão, ou usa o fluxo com `postject`. Em ambos os casos é preciso medir.

I6. **Antivírus.** Um binário Node empacotado, não assinado, que abre portas e sobe processos filhos tem o mesmo perfil do caso do `uv.exe` citado pelo Hermes (fato 1.10). Não medi nada no Windows.

I7. **Sem Docker, o bot não tem isolamento.** Hoje o modo `local` não isola (fato 10.7). Se o app embutido for o padrão sem Docker, a máquina do bot precisa de um aviso explícito, ou o isolamento precisa vir de outro caminho. Os outros produtos usam Docker como uma opção de backend (fato 1.8).

I8. **Tamanho.** PGlite soma cerca de 15,4 MB sem compactar (wasm e data). Postgres nativo no Windows são cerca de 112 MB descompactados (npm) ou 25,5 MB compactados (zonky). O Node empacotado não foi medido (o site oficial do Node não foi testado; os pacotes npm `node-*` não são fonte primária e os tamanhos deles não são confiáveis).

I9. **Migração PC para VPS é um comando, não sincronização.** O OpenBot mostra o caminho: importar agentes e memórias, sem histórico (fato 3.4). Para o Suup, o equivalente seria exportar uma execução fechada ou um bot inteiro, com aviso de que o estado no PC para de valer.

I10. **Sincronização de verdade, se um dia for preciso.** Electric é de leitura: a escrita passaria pela API do Suup. PowerSync mantém um SQLite no cliente e pede Postgres com replicação lógica no servidor. Zero mantém um cliente com replicache e um servidor à parte. Em todos, a cópia local existe, então é preciso definir o dono de cada execução. Uma execução de agente só pode rodar em um lugar, e aprovações e o cofre devem ficar só no servidor autoritativo. Nenhum dos três documentos lidos trata disso para agentes.
