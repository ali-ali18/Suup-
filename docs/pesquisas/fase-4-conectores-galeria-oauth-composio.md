## Pergunta

O dono quer uma **galeria predefinida** de conectores ("lista já definida"), com um clique em Conectar, e acha pesado copiar um token para cada serviço. Hoje o Suup liga conectores MCP por `stdio` (num contêiner) ou por HTTP streamable com um token do cofre (`{{secret:NOME}}`), e **não tem OAuth do MCP**. Perguntas:

1. O que a especificação atual de autorização do MCP exige de um cliente desktop (OAuth 2.1, PKCE, metadados de recurso protegido, registro de cliente por DCR ou por Client ID Metadata Document, redirecionamento de app nativo, renovação), e o que o SDK oficial em TypeScript entrega para o lado do cliente?

3. O que é o Composio (licença do SDK e da plataforma, autenticação, MCP, onde ficam tokens e dados, preço, auto-hospedagem) e quais alternativas abertas e auto-hospedáveis existem (Nango, Pipedream, Arcade)?
4. Como pares fazem isso: Claude Code, Hermes (clone local), OpenClaw?

## Fatos verificados

### 1. Autorização do MCP (especificação 2026-07-28, a mais recente)

- Autorização é opcional e vale para HTTP. Na 2025-11-25: "Authorization is **OPTIONAL** for MCP implementations." e "Implementations using an STDIO transport **SHOULD NOT** follow this specification, and instead retrieve credentials from the environment." (spec 2025-11-25)
- Base de padrões, na 2026-07-28: "OAuth 2.1 IETF DRAFT (draft-ietf-oauth-v2-1-13)", RFC 8414 (metadados do servidor de autorização), RFC 7591 (DCR), RFC 8707 (indicadores de recurso), RFC 9728 (metadados de recurso protegido), RFC 9207 (identificação do emissor), "OAuth Client ID Metadata Documents (draft-ietf-oauth-client-id-metadata-document-00)" e OpenID Connect Discovery.
- Descoberta: "MCP servers MUST implement OAuth 2.0 Protected Resource Metadata (RFC9728). MCP clients MUST use OAuth 2.0 Protected Resource Metadata for authorization server discovery." E: "MCP clients MUST support both discovery mechanisms" (RFC 8414 e OpenID Connect Discovery). O servidor responde 401 com `WWW-Authenticate: Bearer resource_metadata="https://mcp.example.com/.well-known/oauth-protected-resource"` (exemplo da especificação). (spec 2026-07-28)
- Registro do cliente, três mecanismos e a ordem de preferência: "Use pre-registered client information for the server if the client has it available"; "Use Client ID Metadata Documents if the Authorization Server indicates that it supports them (via `client_id_metadata_document_supported` ...)"; "Use Dynamic Client Registration as a fallback if the Authorization Server supports it (via `registration_endpoint` ...)"; "Prompt the user to enter the client information if no other option is available". (Client Registration, 2026-07-28)
- O DCR foi rebaixado na 2026-07-28: "Dynamic Client Registration is deprecated. New implementations should use Client ID Metadata Documents instead." O changelog diz: "Deprecate the OAuth 2.0 Dynamic Client Registration Protocol (RFC7591) as a client registration mechanism in favor of Client ID Metadata Documents". Na 2025-11-25 o DCR ainda era "MAY". (Client Registration e Key Changes, 2026-07-28; spec 2025-11-25)
- Client ID Metadata Document (CIMD): "The `client_id` URL MUST use the "https" scheme and contain a path component"; o documento "MUST include at least the following properties: `client_id`, `client_name`, `redirect_uris`"; o servidor de autorização "MUST validate redirect URIs presented in an authorization request against those in the metadata document". O exemplo da especificação lista `http://127.0.0.1:3000/callback` e `http://localhost:3000/callback` em `redirect_uris`. Anúncio: `"client_id_metadata_document_supported": true`. (Client Registration, 2026-07-28)
- App nativo no DCR: "MCP clients MUST specify an appropriate `application_type` during Dynamic Client Registration." E: "Native applications (desktop applications, mobile apps, CLI tools, and locally-hosted web applications accessed via `localhost`) SHOULD use `application_type: "native"`". (Client Registration, 2026-07-28)
- Redirecionamento: "All redirect URIs MUST be either `localhost` or use HTTPS." E, sobre o risco local: "Client ID Metadata Documents cannot prevent `localhost` URL impersonation by themselves." O servidor de autorização "SHOULD display additional warnings for `localhost`-only redirect URIs" e "MUST clearly display the redirect URI hostname during authorization". (Security Considerations, 2026-07-28)
- PKCE: "MCP clients MUST implement PKCE ... and MUST verify PKCE support before proceeding with authorization." "MCP clients MUST use the `S256` code challenge method when technically capable". "If `code_challenge_methods_supported` is absent, the authorization server does not support PKCE and MCP clients MUST refuse to proceed." (Security Considerations, 2026-07-28)
- Indicador de recurso: o parâmetro `resource` "MUST be included in both authorization requests and token requests." e "MUST identify the MCP server that the client intends to use the token with." (Authorization, 2026-07-28)
- Novo na 2026-07-28, validação do emissor: antes de redirecionar, "the client MUST record the issuer value from the selected authorization server's validated metadata document"; ao receber a resposta, aplica a validação da RFC 9207 antes de enviar o código ao endpoint de token. "MCP authorization servers SHOULD include the `iss` parameter in authorization responses". (Authorization, 2026-07-28)
- Vínculo cliente-servidor de autorização: credenciais pré-registradas ou obtidas por DCR devem ser associadas ao emissor ("keyed by the authorization server's `issuer` identifier") e "MUST NOT" ser reusadas com outro servidor de autorização. (Client Registration, 2026-07-28)
- Escopos: o cliente usa primeiro o `scope` do cabeçalho `WWW-Authenticate` da resposta 401; se não houver, usa `scopes_supported` dos metadados do recurso, "omitting the scope parameter if `scopes_supported` is undefined". Há fluxo de "step-up" para escopos adicionais. (Authorization, 2026-07-28)
- Renovação (refresh): "MUST keep refresh tokens confidential in transit and storage"; "SHOULD include `refresh_token` in their `grant_types` client metadata"; "MAY add `offline_access` to the scope parameter" quando o servidor o anuncia em `scopes_supported`; "MUST NOT assume refresh tokens will be issued; the AS retains discretion". (Authorization, 2026-07-28)
- Também na 2026-07-28: remoção das sessões de protocolo e do cabeçalho `Mcp-Session-Id` do transporte streamable HTTP (primeiro item de "Major changes", changelog). Relevante porque o SDK 1.x fala a revisão anterior (abaixo).
- RFC 8252 (URIs de redirecionamento de apps nativos, interface de loopback `http://127.0.0.1:<porta>`): texto da RFC **não verificado (host bloqueado)**. O que está verificado é o que a especificação do MCP e os pares fazem com loopback (acima e nas seções 4 e 5).

### 2. SDK oficial `@modelcontextprotocol/sdk` 1.32.2 (lado do cliente)

- Versão `latest` no npm em 23/11/2026: 1.32.2, licença MIT, autor "Anthropic, PBC". A revisão mais recente do protocolo que ele declara é a **2025-11-25**: `LATEST_PROTOCOL_VERSION = '2025-11-25'` em `dist/esm/types.js` (a 2026-07-28 **não** está na lista `SUPPORTED_PROTOCOL_VERSIONS`).
- A interface `OAuthClientProvider` (arquivo `client/auth.d.ts`) é implementada pelo aplicativo e tem: `redirectUrl`, `clientMetadata`, `clientMetadataUrl?` ("External URL the server should use to fetch client metadata document"), `clientInformation()`, `saveClientInformation?` ("If implemented, this permits the OAuth client to dynamically register with the server"), `tokens()`, `saveTokens()`, `redirectToAuthorization(url)`, `saveCodeVerifier()`/`codeVerifier()`, `invalidateCredentials?`, `saveDiscoveryState?`/`discoveryState?` e `addClientAuthentication?`. Texto da interface: "Implements an end-to-end OAuth client to be used with one MCP server. ... Tokens, authorization codes, and code verifiers should not cross different sessions."
- Funções exportadas: `auth()` ("Orchestrates the full auth flow with a server"), `discoverOAuthProtectedResourceMetadata`, `discoverAuthorizationServerMetadata`, `startAuthorization`, `exchangeAuthorization`, `refreshAuthorization`, `registerClient` (DCR), `fetchToken`, `extractWWWAuthenticateParams`, `selectResourceURL`.
- CIMD no SDK: em `auth.js`, `supportsUrlBasedClientId = metadata?.client_id_metadata_document_supported === true` e, se o provedor tem `clientMetadataUrl` HTTPS, o `client_id` passa a ser essa URL.
- Renovação: `auth.js` usa o `refresh_token` guardado e `refreshAuthorization` faz `grant_type: 'refresh_token'`. O transporte `StreamableHTTPClientTransport` aceita `authProvider`: tenta com o token atual, "If the access token has expired, the `authProvider` is used to refresh the token", e depois do redirecionamento do usuário chama-se `finishAuth(authorizationCode)` antes de tentar de novo; sem `authProvider`, lança `UnauthorizedError`.
- Dos itens novos da 2026-07-28, a busca por `iss` e `application_type` em `client/auth.js` da 1.32.2 não achou nada. O pacote `@modelcontextprotocol/client` 2.4.0 (Apache-2.0, Node >=20) contém a string `2026-07-28`, `recordedIssuer` e `authorization_response_iss_parameter_supported` nos arquivos de distribuição (só busca de texto; o código não foi lido nem executado).
- O SDK não abre o navegador nem sobe o servidor de retorno: isso é do aplicativo (`redirectToAuthorization` e a captura do `code`).

### 3. GitHub

- `github/github-mcp-server`, licença MIT ("Copyright (c) 2025 GitHub").
- Remoto: `https://api.githubcopilot.com/mcp/`. O README mostra duas configurações, "Using OAuth" e "Using a GitHub PAT", e avisa: "Each MCP host application needs to configure a GitHub App or OAuth App to support remote access via OAuth. Any host application that supports remote MCP servers should support the remote GitHub server with PAT authentication."
- A documentação do Claude Code, no exemplo do GitHub: "GitHub's remote MCP server authenticates with a GitHub personal access token passed as a header." (`claude mcp add --transport http github https://api.githubcopilot.com/mcp/ --header "Authorization: Bearer YOUR_GITHUB_PAT"`). Ou seja, o Claude Code usa PAT, não o OAuth do MCP, com esse servidor.
- Toolsets e somente leitura no remoto, por cabeçalho: `X-MCP-Toolsets` ("Comma-separated list of toolsets to enable"), `X-MCP-Tools`, `X-MCP-Readonly` ("Enables only "read" tools."), `X-MCP-Lockdown` ("a best-effort content filter, not a security boundary"). Também por URL: "Add `/readonly` to the end of any URL". No servidor local: `--toolsets`, `--tools` e `--read-only` ("Read-only mode takes priority: write tools are skipped if `--read-only` is set, even if explicitly requested via `--tools`").
- Servidor local (`stdio`, binário ou imagem `ghcr.io/github/github-mcp-server`) com OAuth embutido: "Official released binaries and the `ghcr.io/github/github-mcp-server` image ship with a registered GitHub OAuth application baked in, so on **github.com** you can start the server with no token and no client ID at all." Usa "authorization code flow with PKCE", sobe um servidor de retorno em loopback, e guarda o token "in memory only". Em contêiner, precisa de porta fixa publicada em loopback (`GITHUB_OAUTH_CALLBACK_PORT`, exemplo `127.0.0.1:8085`); sem porta, cai no "device-code flow" (código curto e URL `https://github.com/login/device`). A própria documentação admite: o segredo do cliente embutido "is **not truly confidential** — PKCE is what secures the flow". Tokens que expiram (GitHub App) são renovados com o refresh token. Para GitHub Enterprise Server ou `ghe.com`, é preciso um app próprio (`--oauth-client-id`).
- Variável `GITHUB_PERSONAL_ACCESS_TOKEN` "takes precedence over OAuth".

### 9. Composio

- O repositório `ComposioHQ/composio` traz o SDK (TypeScript `@composio/core`, Python `composio`), a CLI e os adaptadores de provedores. Licença do repositório: "MIT. See LICENSE." (arquivo MIT, "Copyright (c) 2025 Sampark Inc."). O campo `license` do pacote npm `@composio/core` 0.31.0 diz **ISC** (diverge do arquivo do repositório). Uma fonte aberta para o **SDK**; a plataforma que ele chama é hospedada (o SDK precisa de chave de API: `new Composio({ apiKey: 'your_api_key' })`).
- Modelo: "A **session** is the runtime context for an agentic run ... it ties together the user, the toolkits available, authentication, and connected accounts." Autenticação é por usuário (`userID` escolhido por você): "Composio stores connections under that ID".
- Como a autenticação funciona: "Composio manages the OAuth redirects, token exchange, and refresh." ## Inferências

Rotuladas como inferência: são conclusões minhas a partir das fontes, não afirmações delas.

1. **O caminho nativo cabe no que o Suup já tem.** O SDK que o Suup usa (`@modelcontextprotocol/sdk` 1.x) já traz descoberta, PKCE, CIMD, DCR e renovação; falta o aplicativo implementar `OAuthClientProvider` (guardar tokens no cofre, abrir o navegador, receber o `code` em loopback). Não é preciso reescrever o protocolo.
2. **Um cliente desktop sem relacionamento prévio com cada servidor deve preferir CIMD e cair para DCR.** Isso segue a ordem da especificação (pré-registro, CIMD, DCR, pedir ao usuário). CIMD exige uma URL HTTPS pública com o documento do cliente; para um app 100% local e de código aberto, isso significa publicar um arquivo estático num endereço estável (o Hermes faz isso no GitHub Pages) ou aceitar só DCR.
3. **DCR ainda é o que a maioria dos servidores hospedados aceita hoje**, pelas observações do Hermes (Atlassian "verified live", Linear e Notion como OAuth nativo), mas a especificação o chama de obsoleto: o Suup precisa dos dois mecanismos e do pré-registro.
4. **Há servidores que escolhem clientes por nome.** Se a observação do Hermes sobre o Figma estiver certa, o Figma recusa o registro de clientes que não estão na lista dele ("Hermes Agent" deu 403), então um app novo não consegue o "um clique" nesse servidor sem acordo com o Figma ou sem registrar um app próprio. Fingir ser "Claude Code" (o que o Hermes faz) contraria a regra do dono de ser honesto; não recomendo.
5. **GitHub: o "um clique" vem do servidor local, não do remoto.** O remoto exige que cada aplicativo hospedeiro tenha seu GitHub App/OAuth App, ou usa PAT; o servidor `stdio` oficial traz um app OAuth embutido e faz loopback + PKCE sozinho. Com o Suup rodando o conector num contêiner, isso pede uma porta de retorno publicada em loopback, ou o fluxo de código de dispositivo (que não precisa de porta e combina com a regra de segredo nunca no chat).
6. **O Google é a exceção que exige o dono.** Gmail, Agenda e Drive via servidor aberto pedem um cliente OAuth do Google Cloud; um app não verificado só serve ao dono e a usuários de teste, e o `gws` fala em limite de escopos. O que o Google exige para publicar um app com escopos sensíveis ou restritos **não foi lido**; então não dá para prometer ao dono um "Conectar Google" de um clique para outras pessoas sem essa leitura.
7. **Composio resolve a dor do token, mas troca por dependência e por terceiros guardando tudo.** Os tokens OAuth de todos os serviços ficam na plataforma hospedada da Composio, as chamadas passam por ela, e na autenticação gerenciada o usuário autoriza "Composio", não o Suup. O SDK é aberto, a plataforma não é (preço, auto-hospedagem e política de dados não verificados). Isso é incompatível com ser o padrão num produto "100% aberto, sem prender a provedor"; cabe como entrada opcional, com aviso.
8. **O Composio Connect cabe no modelo atual do Suup.** É um ponto MCP HTTP com cabeçalho `x-consumer-api-key`, ou seja, um conector HTTP com `--header-secret x-consumer-api-key=COMPOSIO_KEY`, que já funciona hoje sem OAuth. As ferramentas viriam como 7 metaferramentas, e o poder de executar qualquer app fica atrás de poucas metaferramentas genéricas, o que desgasta a concessão por ferramenta do Suup (o cartão mostraria uma ferramenta genérica). A conclusão sobre o cartão é inferência: depende dos argumentos que cada metaferramenta recebe, que não li.
9. **Nango, Pipedream e Arcade não são "abertos" no sentido da regra do dono** (Elastic 2.0 e fonte disponível não são licenças aprovadas pela OSI; no Arcade só o framework de servidores é MIT). Se o dono quiser uma camada de OAuth auto-hospedada e aberta, nenhuma das três atende sem concessão, pelo que li.
10. **A galeria curada do Hermes é o desenho de referência e a regra dele coincide com a do Suup**: entrada = aprovação do dono, manifesto fixa o transporte, nada de busca livre. O Suup pode seguir isso, mantendo as ferramentas de cada entrada com a concessão por ferramenta que já existe.
11. **A revisão 2026-07-28 do protocolo muda o transporte** (sem `Mcp-Session-Id`) e acrescenta a validação do emissor. O SDK 1.32.2 fala a 2025-11-25; servidores que só falarem a revisão nova podem exigir o pacote 2.x, o que o Suup não verificou (não testei compatibilidade). A escolha de migrar é decisão à parte.

## Adendo (23/11/2026): o retorno numa VPS

Decisão do dono: nada de colar o endereço de retorno ("Mas por que raios eu colaria um link?"). Com a regra citada acima ("All redirect URIs MUST be either `localhost` or use HTTPS", Security Considerations, revisão 2026-07-28 da especificação de autorização do MCP, https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization, lida em 23/11/2026), uma VPS só recebe o navegador num endereço **HTTPS** dela: `server.publicUrl`, com a rota `/oauth/callback`. As conferências do retorno (state de uso único, `iss` da RFC 9207, PKCE) não mudam com o lugar. Sem endereço público, o login por OAuth não é oferecido numa VPS; as entradas por token seguem.
